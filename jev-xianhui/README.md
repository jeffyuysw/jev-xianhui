# 先回 · 消息优先级助手

> 手机通知太多，分不清哪条非回不可？让 AI 告诉你先回哪个。

一个 Android 小应用：**读取手机通知 → 判断哪条必须马上回 → 结果放在可拖动的悬浮窗里**。默认贴在屏幕左边，点某条直接跳回那个会话。

**由 [Jev](https://github.com/typesafeinc/jev) 判断模型驱动**（TypeSafe 的 System One 决策模型，不是大语言模型）—— 它不生成文字，只回答"选哪个 / 打几分 / 是不是"，所以一次判断约 1 秒、约 $0.00004。

## 本项目参考与二次开发来源

本项目由 **[jev-chat-jarvis](https://github.com/jev-chat/jev-chat-jarvis)** 开源代码进行二次开发而完成。准确地说，是**复用它的判断契约、替换它的采集方式、删除它的生成层**：

| 维度 | 与 jev-chat-jarvis 的关系 |
| --- | --- |
| 模型调用契约 | **复用** —— 沿用 `noul / choice / score` 三种题型的请求与解析格式 |
| 题目设计口径 | **同源** —— 本题的四道题由它的七道题按需裁剪改写（英文 instructions + 中文 state） |
| 采集方式（Android） | **替换** —— 它用无障碍读屏，本应用改用 Android 官方通知监听 API |
| 生成层 | **删除** —— 它用大模型起草候选回复，本应用完全不生成文字 |
| 产品形态 | **不同** —— 它回答"该怎么回"，本应用回答"先回哪个" |

关键在于：**jev-chat-jarvis 是"Jev 判断 + DeepSeek 生成"的双模型架构，本应用只保留 Jev 那一层，是一个纯判断型工具。**

## 特性

- **只判断，不代回** —— 帮你决定优先级，回复永远由你自己发
- **不用打开微信** —— 靠系统通知工作，任何发通知的 App 都能接；**停在微信里时也照常监听**（见[监听模式](#监听模式仅后台监听)）
- **不碰无障碍服务** —— 用 Android 官方 `NotificationListenerService`，不伪装、不绕过、不读聊天记录
- **可拖动悬浮窗** —— 松手自动贴边不挡内容，可折叠成计数条；**高度随消息数量伸缩**（没消息时是一条细条）
- **外观可自定义** —— 背景色 / 文字色 / 字号 / 宽度 / 不透明度都能改，RGB 自选，默认白底黑字
- **整行可点** —— 点条目跳进会话并自动消除该条（列表和通知栏同时清）
- **开机自动恢复** —— 重启手机或更新 App 后自动重新绑定监听；运行中每 30 秒自检一次，被系统解绑会自己拉回来
- **连接状态可见** —— 主页「运行」区直接显示"监听服务：已连接 / 未连接"，不用进系统设置猜
- **消息不落盘** —— 只在判断那一刻发给模型，不留历史
- **极低成本** —— 每天 200 条消息约半分钱

## 界面与操作

**主页**是三张设置卡，每张独立显示自己的状态：未完成时是红色徽章 + 按钮，完成后变绿徽章、按钮自动消失。顶部有一条总览，直接告诉你"还差几步"。运行区下方实时显示当前待处理条数。

**悬浮窗**有两种形态：

| 操作 | 效果 |
| --- | --- |
| 按住顶部横条拖动 | 移动位置，**松手自动吸附到最近的屏幕边缘** |
| 点一下顶部横条 | 收起 / 展开列表 |
| 点某条消息 | 跳进那个会话，同时该条从列表和通知栏消失 |
| 点「全部已读」 | 清空列表，并清掉对应的系统通知 |
| 点「×」 | 关闭悬浮窗，回主页可重新打开 |

颜色含义：**红=马上回**，**黄=尽快**，**灰=可以晚点**，**蓝=正在判断**。判断失败的条目点一下即可重试。

### 监听模式：仅后台监听

「运行」区有一个开关 **「仅后台监听」，默认关闭**。

| 开关 | 行为 |
| --- | --- |
| 关闭（默认） | 不管停在微信里，还是切到后台 / 锁屏，收到的消息都进列表 |
| 打开 | 只保留后台消息，停在微信里收到的消息不再进列表 |

微信切到前台的那一刻会**把自己刚弹的通知撤回**（系统回调里的 `REASON_APP_CANCEL`）。以前这个撤回被当成「用户已经处理掉了」，于是行刚建好就被删掉 —— 看起来就像「一进微信就监听不到消息」。关闭该开关时只认**真正的用户操作**（划掉通知、点通知、清空通知栏），App 自己撤回不算数；打开则恢复旧规则，通知离开通知栏就删行。

## 悬浮窗外观

主页底部「悬浮窗外观」一栏可以改五项，改动**立即生效**，无需重启：

| 项目 | 范围 | 默认 |
| --- | --- | --- |
| 背景色 | 6 个预设色块 + RGB 自选 | `#FFFFFF` 白 |
| 文字色 | 6 个预设色块 + RGB 自选 | `#2C2C2A` 近黑 |
| 字号 | 10 – 20 sp | 12 sp |
| 宽度 | 180 – 340 dp | 220 dp |
| 不透明度 | 1 – 100 % | 100 % |

「自定义 RGB」打开一个 R/G/B 三条滑杆的对话框，上面带实时预览，比色轮更容易对着现成主题配色。另有两个快捷按钮：**黑白反转**（一键交换前景/背景，做深色模式）和**恢复默认**。

**不透明度**调低后整块悬浮窗半透明，能看清底下的微信而不挡住内容。最低 1% 而不是 0 —— 完全透明的卡片仍然会接收点击，却看不见也拖不动。它是作用在**整个窗口**上的（`LayoutParams.alpha`），不是逐个 View 设，所以卡片底色、文字、颜色条一起淡出，没有叠加接缝。

### 高度随内容伸缩

悬浮窗**没有固定高度**，它随队列长度变化：

| 状态 | 列表高度 |
| --- | --- |
| 没有消息 | **40 dp**（一条细条，只放一行提示） |
| 有消息 | 按实际行高累加，逐条长高 |
| 消息很多 | 封顶 300 dp，再多就**在卡片内滚动**，不再继续变高 |

空着的时候它是一条很细的条，不会占掉小半个屏幕。上限 300 dp 是防止消息堆积时把屏幕盖满。

> 实现细节：`ScrollView` 原先写死 300 dp，改由 `fitScroller()` 在子视图布局完成后测量内容高度并回写 `layoutParams.height`。测量必须 `post` 到布局之后，否则此时宽度还是 0，量出来的高度不对。

你只选两个颜色就够了 —— 行底色、描边、次要文字、四个优先级强调色全部由这两个颜色**推导**出来（见 `overlay/OverlayPalette.kt`）。所以深色底会自动用浅色强调色，不会出现"深色底上看不清红点"的情况。

设置界面实时检查对比度：低于 3:1 提示"几乎看不清"，低于 4.5:1 提示"偏低"，但**不会阻止你选**。

> 两端配色**各自独立保存**：Android 存在 SharedPreferences（`overlayBg` / `overlayFg` / `overlayFontSize` / `overlayWidth` / `overlayOpacity`），Windows 存在 `config.json`，互不同步。

## 工作原理

```
系统通知（微信/QQ/任何 App）
        ↓  NotificationListenerService
   提取 标题 + 正文（拆出群消息发送者）
        ↓
   一次请求问 Jev 四件事：
   ┌────────────────────────────────────┐
   │ 1. 紧急度？        → 打 1–9 分      │
   │ 2. 要马上回？      → 是 / 否        │
   │ 3. 什么类型？      → 工作/私人/推广… │
   │ 4. 为什么急？      → 有时限/对方在等… │
   └────────────────────────────────────┘
        ↓
   分档 → 悬浮窗显示（红 / 黄 / 灰）
```

分档规则（`core/MsgItem.kt`）：

| 紧急度 | 分档 | 颜色 |
| --- | --- | --- |
| 要马上回，或 ≥ 7 分 | **马上回** | 红 |
| ≥ 4 分 | 尽快 | 黄 |
| < 4 分 | 可以晚点 | 灰 |
| 还没判断完 | 判断中 | 蓝 |

## 和 jev-chat-jarvis 的区别

如果你在看那个项目 —— 它做的是"读当前聊天窗 → 判断对方意图 → **给候选回复**"，本应用只取它一半能力：**判断**，去掉回复生成。

更关键的是消息来源不同：

| | jev-chat-jarvis | 本应用 |
| --- | --- | --- |
| 读消息方式 | 无障碍服务读当前界面 | **通知监听（官方 API）** |
| 要不要打开微信 | 必须打开 | 不需要 |
| 是否要伪装系统服务 | 是（微信 8.0.52+ 混淆节点） | **不需要** |
| 能否覆盖其他 App | 只适配过的几个 | 任何发通知的 App |
| 合规风险 | 绕过微信混淆，灰区 | 官方 API，用户手动授权 |

代价是只能拿到通知里的文字（长消息被系统截断），拿不到完整聊天上下文 —— 但对"要不要马上回"来说，第一句话通常够了。

## 项目结构

```
app/src/main/java/com/jev/priority/
├── core/
│   ├── MsgItem.kt              # 一条待处理会话 + 紧急度分档规则
│   ├── MsgStore.kt             # 内存列表、排序、变更通知
│   └── Prefs.kt                # 设置（密钥存 App 私有空间）
├── jev/
│   ├── HttpJson.kt             # 唯一的网络出口
│   ├── PriorityQuestions.kt    # ★ 四道判断题 —— 效果主要看这里
│   └── PriorityClient.kt       # 调模型并解析结果
├── notify/
│   ├── MsgNotificationListener.kt   # 读通知、拆分群消息发送者、撤销通知
│   ├── NotificationListenerHolder.kt # 让悬浮窗能反向调监听器
│   └── KeepAliveService.kt          # 前台服务保活
├── overlay/
│   ├── PriorityOverlay.kt      # 可拖动悬浮窗（贴边吸附 / 折叠 / 整行点击）
│   └── PriorityRetry.kt        # 判断失败的单条重试
└── MainActivity.kt             # 三步设置卡与状态总览
```

**想改进判断质量，只需要动 `PriorityQuestions.kt` 一个文件。**

重新生成：

```bash
python ../tools/make_icons.py
```

> 注意：源图 `icon.png` 四角是白色（非透明），且**没有一个透明像素**。脚本会用圆角矩形几何蒙版把圆角外区域处理掉——自适应图标前景层填品牌蓝，其余图标抠成透明。**不要**改用"接近白色就替换"的判定方式，那会把图标内部的白色气泡与「先回」文字一起吃掉。

## 已知限制

- **长消息被截断** —— 通知里只有开头一截，看不到完整上下文
- **微信在前台时可能根本不发通知** —— 多数情况下微信是「先发出、再秒撤回」，默认的监听模式能接住；但如果它整个不生成通知，第三方应用没有别的合法途径拿到内容
- **国产 ROM 需手动保活** —— MIUI/HyperOS 等要加白名单，详见[部署文档](docs/DEPLOY.md#让它在后台活下来必做)
- **初次判断有约 1 秒延迟** —— 是网络往返，判定前显示"判断中"
- **不持久化** —— 重启 App 列表清空（有意为之，避免留聊天痕迹）

## 隐私

- API Key 只存 App 私有存储
- 消息原文只在判断那一刻发给模型接口，**不落盘、不进日志、不存历史**
- 无统计、无埋点、无上报

唯一的网络出口是 `jev/HttpJson.kt` 里那一个 POST，可自行抓包验证。

## 合规

使用 Android **官方** `NotificationListenerService` API。不 Root、不伪造系统服务、不绕过应用安全机制、不读取聊天数据库。

请仅在自己拥有或已获授权的设备上使用，遵守各软件用户协议与当地法律法规。
